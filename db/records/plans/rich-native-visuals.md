Build one native visual component system that ordinary workbook spaces, Home, programmable mini apps and useful inline chat surfaces can all use. The agent chooses the representation, binds real workbook data and invokes semantic operations. The host owns layout, rendering, interaction feedback, arithmetic and access. A chart in a mini app must be as capable and inspectable as the same chart on Home, with a readable compact representation available in chat. Reusing components does not mean every view shares filters or every chart reads the same dataset.

Keep the product centered on completed business work: the conversation changes the work; the visual surface explains its state and supports fast inspection. Direct manipulation remains a useful optional shortcut. A user should never have to drag a card, click a chart or select a hidden tab to make a business operation possible through chat.

The first usable chat increment supplies structured questions, compact inputs and exact review/outcome controls. The next bounded increment is P1-image: included images in chat and standalone Home views, reusing the existing mini-app support. It does not wait for chart queries or diagram layout. The chart-and-exceptions workflow then spans inline chat, a mini app and Home. The full program also includes boards, timelines/calendar views, relationship/process diagrams, images, richer tables and flexible composition. Finish each usable increment before advancing. Do not treat this document as authorization to replace the active installed app, toggle VoiceOver or change system settings; those existing operating boundaries remain.

## 2. The intended experience

### Three anchor journeys

1. **Sales and collections.** Drop an invoice workbook into chat; ask, “Show monthly invoicing and overdue balances.” The app opens on a dated trend and a short overdue table, with currency, reporting period and exclusions visible. Selecting a month narrows the detail table. “Show only Acme, then pin this overview to Home” produces the same result without pointer use. Marking an invoice paid invokes the existing validated business action, updates both surfaces and can be undone. Neither chart counts the worksheet header or subtotal as an invoice.
2. **Stock and purchasing.** “Show what needs reordering.” The app prioritizes shortage exceptions, then a stock-versus-reorder-level chart and an optional product-image detail. “Receive 12 bolts” changes the underlying inventory action once. Home displays the compact shortage view, not a second inventory database or a copy of the entire input form.
3. **Jobs and dependencies.** “Show my jobs by stage and what is due next week.” A board and timeline show the same jobs. “Move job J-12 to Doing and move its due date to Friday” uses named actions with normal validation. A dependency view explains why a job is blocked; it does not infer a dependency just because two tasks are nearby. Invalid moves keep the original state visible and explain the refusal.

Each journey must remain useful with the model unloaded after the app is created. Native selection, scrolling, tooltips, filtering and already defined actions cannot require an inference turn. Interpreting a new natural-language request can still require the local model; direct semantic operations and known controls do not. This is not a promise of model-free language understanding.

### Composition and visual language

Use the project's native macOS direction: system typography, semantic light/dark colors, precise alignment and a restrained 4-point spacing scale. Richness comes from useful encodings, clear hierarchy, imagery when relevant and well-composed views. Avoid identical card grids, giant metric walls, ornamental sparklines, oversized form panels and nested boxes.

Provide a small composition grammar: `Stack`, `Inline` with wrapping, `AdaptiveGrid`, `Split`, `Section`, `Tabs` and `Disclosure`. These are proposed capabilities, not renamed shipped APIs. Preserve recognizable existing Row/Column APIs where suitable; share underlying layout policy. Each child can declare semantic role, minimum readable width, bounded preferred height and priority. Grid tracks are chosen from the available container width, not a global screen breakpoint. Content remains in a predictable reading order. A detail inspector becomes an inline disclosure at narrow widths. Minimum adaptive behavior, semantic reading order and typography tokens ship in P1; P2 expands composition rather than repairing an unusable first release. Canvas viewports can pan; ordinary screens must not require horizontal scrolling to reach primary content.

Use semantic typography roles (`title`, `section`, `body`, `caption`, `metric`), spacing/density tokens and finite status/series palettes. Keep low-level bounded size/spacing controls for genuinely custom compositions. Colors distinguish status and series, with labels, symbols or line patterns carrying the same meaning. Use stable record/group/series keys separate from display labels; duplicate labels must not merge entities. Declare category/time ordering with deterministic tie-breaks and show a clear selection state when a previously selected entity is removed. Assign series colors from stable series identities; filtering or sorting must not recolor the remaining categories. Do not promise arbitrary CSS, gradients, downloaded fonts or per-app themes.

Home remains a calm overview: attention first, a small number of explicitly selected views and a clear way to resume. Compact views preserve units, period, coverage and the key question; they reduce secondary detail rather than shrink text. Open app restores the relevant view and context. No automatic rearrangement of a person's authored Home.

### Controls, states and motion

Keep charts/data prominent and operations secondary: “Show overdue,” “Group by customer,” “Explain this change,” and “Open records” are more useful than a toolbar of unlabeled icons. A compact view menu offers Inspect data, Change view in chat, Add to Home, Expand and, when implemented, Export. Use the existing composer handoff and preserve unsent text.

Every component defines loading, empty, filtered-empty, partial, invalid-data, stale, unavailable-source, permission-disabled and failed states. Zero is a result; missing is unknown; not yet loaded is neither. Keep the last valid display during refresh with visible freshness when relevant; a failed refresh cannot silently relabel old data as current. Retry is scoped and cancellable. Motion preserves object identity and explains a change; respect reduced motion. Hover cannot be the only path to information. Selection/focus survives ordinary data refresh when the entity still exists.

| Component family | Required useful capability | Priority and limits |
| --- | --- | --- |

P2 adds stacked bars/area, scatter, histogram and heatmap. No 3D; dual axes are outside initial scope. |
| Metric and comparison | Exact value, unit, reporting period, optional target/baseline, absolute and percent change; meaningful short trend. | P1. Absolute delta requires compatible units and comparable periods. Percent change defaults to (current - baseline) / baseline only for a positive baseline; zero/negative/missing baselines show unavailable percentage with an explanation. | AssetImage and Attachment | Included-image display, captions/accessible description, proportional fit and full inspection in chat, mini apps and Home; other attachments open the existing viewer. | P1-image for basic cross-surface display. P4 adds repeated record thumbnails only within explicit bindings. |
| Text and annotations | Paragraphs, lists, emphasized text, callouts and structured record/source links; compact labels on visuals. | P2. Use a bounded rich-text AST and existing Markdown parsing where appropriate; no HTML execution. |

Part-to-whole charts are optional P2: a small positive-category donut can be useful, but bars remain the comparison default. Histograms declare bin origin/width or exact edges, boundary inclusion and overflow handling so every included value belongs to exactly one bin. Heatmaps declare matrix axes, color scale/legend and distinct missing-versus-zero cells. Stacked charts require compatible units, separate positive/negative baselines and explicit normalization if shown as percentages; area fills may not bridge unknown intervals. Logarithmic/dual axes and smoothing remain outside the first two releases unless separately specified and accepted. Image galleries, pivot-table authoring, maps, Sankey, treemap, arbitrary SVG execution, 3D, video/audio editors and a Figma-like canvas are outside this program. Keep extension points without claiming those features.

## 4. Shared contract and implementation architecture

### One declarative specification, three surface adapters

Add validated Codable/Sendable `VisualDefinition`, `VisualDataRequest`, `VisualResult`, `VisualSelection` and `VisualPresentation` types in SevraCore. These names are proposed. A discriminated component specification describes purpose, bindings, encodings, format, layout and interactions. Nested fields have bounded typed schemas and unknown keys fail closed; an unrestricted JSON props bag would hide mistakes instead of creating flexibility. It is data, never arbitrary Swift, JavaScript, SQL or HTML. Keep source/business logic out of styling fields. Immutable package descriptors and versioned presentation overrides are different layers of this same contract; neither is a second business-rule implementation.

Ordinary `Component` owns a visual specification within the existing versioned SpaceDefinition. NativeAppPackage declares at most 16 named `views`, with a proposed combined descriptor bound of 128 KiB inside the existing 1 MiB total package limit and 512 KiB source limit; a new SDK visual node references one of those names. Both resolve to the same host evaluator and native renderer. New code should not duplicate chart parsing or business totals inside the JS runtime. Generate matching protocol validation, TypeScript declarations, discovery documentation and grammar fixtures from one catalog where practical; runtime validation remains authoritative.

A proposed native-app chart descriptor excerpt is below. It is not a complete runnable package: `invoiceDetails`, its typed customer parameter and the dataset binding must also be declared and validated in the P0 fixture. It deliberately uses already typed decimal data; Excel text projection is the separate required contract below. Dataset/column names are illustrative and must be discovered, not guessed. The example assumes inspected accepted/actual rows, a currency column and a stable customer-key column; those values are illustrative, not automatic filters for every workbook. The query body uses the existing alias-based app query shape; the outer visual fields are proposed. Ordinary spaces resolve the same logical bindings through their own workbook-owned binding map.

```json
{
  "id": "salesByCustomer",
  "kind": "chart",
  "data": {
    "query": {
      "sources": [{"table": "invoices", "scope": {"meaning": "actual", "status": "accepted"}}],
      "select": [
        {"id": "customer", "column": {"source": 0, "column": "customer"}},
        {"id": "net", "column": {"source": 0, "column": "net"}, "aggregate": "sum"}
      ],
      "filters": [{"column": {"source": 0, "column": "currency"}, "op": "eq", "value": "USD"}],
      "groupBy": [{"source": 0, "column": "customer"}],
      "sort": [{"field": "net", "descending": true}, {"field": "customer", "descending": false}],
      "limit": 1000
    },
    "coverage": "completeGroups"
  },
  "mark": "bar",
  "encoding": {
    "x": {"field": "customer", "type": "category"},
    "y": {"field": "net", "type": "decimal", "unit": "USD"}
  },
  "presentation": {"title": "Net invoicing by customer", "density": "comfortable"},
  "interactions": {"selection": {"kind": "group", "targets": [{"view": "invoiceDetails", "parameter": "customer", "valueField": "customer"}]}}
}
```

The proposed `Sevra.View` SDK node takes a declared view ID and optional presentation-record ID. Both resolve through the host catalog; no arbitrary callback/string in the descriptor becomes executable code. Family-specific factories may produce these typed definitions, but must not create a second wire format. All target IDs must resolve within the same authorized view set. Here invoiceDetails must declare a typed customer parameter. A view with adjustable filters declares bounded `parameters` (type, default, allowed values/range) and fixed slots in its query. The host validates values before substituting literals; parameters cannot supply column names, source identities, raw predicates or SQL. Selection-target mappings name the target parameter and source field explicitly. Clearing a selection is distinct from selecting a group whose value is null. Undeclared parameters, incompatible target types and cyclic filter propagation are refused. Changes carry an origin/event token and publish once, so two linked views cannot create an update loop. `completeGroups` refuses a `hasMore` result; it does not enlarge the query limit or hide omitted customers. The Home binding adds `viewID` and optional `presentationID` to the existing app reference. P0-chat freezes the publication envelope; P1-image freezes the canonical visual owner/reference/presentation foundation and image discriminator; P0-visual extends those same types with chart/query contracts. Each stage freezes required/allowed keys, stable identity, fixtures and invalid-field diagnostics before implementing its adapters. It must not create another owner store or defer basic images until chart queries exist.

Create a `SevraVisualUI` target depending on Core and native Apple frameworks, plus the proposed lower-level `SevraMedia` module when P1-image lands. Dependency direction is Core types/evaluation -> VisualUI -> ordinary-space, mini-app and conversation adapters. PreviewUI depends on VisualUI for conversation surfaces; VisualUI never depends on PreviewUI. TableUI remains Core-only, with shared formatting in Core and adapters avoiding a TableUI/VisualUI cycle. VisualUI receives narrow host-owned data/action closures; it cannot manufacture a NativeAppAccess grant or import SevraAppUI. AppKit mounting and session authority stay in SevraAppUI. SevraApp, SevraAppUI and SevraPreviewUI consume it, avoiding a reverse dependency on the main executable. SwiftUI chart views are hosted with NSHostingView inside the existing AppKit renderer. Preserve mounted identity instead of replacing the hosting view on each patch. Native tables retain NSTableView recycling; shared column presentation lives below both existing table frontends, using Core formatting/rule types and the lower-level table UI target where appropriate. Do not make VisualUI import the mini-app AppTable class or rewrite both transactional editors merely to share formatting. The chart renderer is shared directly; existing table adapters share tested presentation rules while retaining their data/edit adapters. Use AppKit/Core Graphics for dense diagrams with explicit hit-testing/accessibility elements. A SwiftUI Canvas alone does not supply per-element interaction or accessibility.

### Data correctness before drawing

Reuse the typed DatasetQuery compiler, exact Decimal aggregate functions, cancellation and snapshot identity. Preserve its existing bounds: up to three sources, 1,000 output rows per page, 100,000 contributing rows/32 MiB referenced inputs, four million VM instructions and a maximum three-second query deadline. Native-app responses retain their smaller 1 MiB boundary. Return a bounded visual result directly to the native host, not thousands of rows serialized through app JavaScript.

The evaluation order is declared record domain/header exclusions, typed projection, relational filtering/joins, grouping/aggregation, output sorting, then bounded presentation. Never parse a known header into a number before applying its declared exclusion. Reuse existing number/date and Excel date-system implementations where they meet this contract; do not introduce a second formula engine. Add only explicit typed projection operations needed by visuals: parse decimal with declared locale/format, parse date with declared format/date system, time bucket with calendar/time zone, and numeric bin with a specified rule. They run within the same query budget and read transaction. Saved-query validation, managed-schema checks and ad hoc/app-query compilation must accept exactly the same extension. Source scopes for meaning/status/scenario are explicit; a visually labeled actual-only result cannot default to all current members when forecasts or drafts share its source. Imported Excel views specify body rows/range and exclusion of known headers/totals using inspected evidence; never globally infer that row 1 is a header or that any row called Total should disappear. Typed projections do not rewrite original cells or formula outputs. Ambiguous dates/numbers require a choice. Parsing failures produce counted, inspectable exclusions or refuse a requested total; never silently become zero.

VisualResult carries query/spec identity, workbook read revision, columns/types/units, rows or aggregates, coverage, excluded/null counts and the parameters that produced it. Cache identity includes authorization scope/epoch and physical workbook, not just query text. Never serve a previously authorized result to a narrower or revoked caller. Distinguish complete population aggregation from a limited list of output groups or plotted marks. `hasMore` must trigger explicit grouping/filtering/paging, not a chart of the first page masquerading as the whole. Never compute a total from a paginated table. P2 may add an explicit ranked-subset display mode: its title and coverage state the rank/limit, and an Other group is legal only when calculated over the complete remainder. A query page cannot invent Other or a denominator. Use Decimal values for all business arithmetic; conversion to finite Double occurs only at plotting coordinates. Detect overflow, underflow-to-zero and materially collapsed coordinates before drawing; offer a declared scaled unit or exact table instead of a misleading plot. Exact labels, comparisons and inspection retain normalized Decimal values; averages and percentages declare precision/rounding instead of promising infinite exactness.

Joins require an explicit expected cardinality or a pre-aggregation that preserves the intended measure. Fixtures must catch duplicated invoice amounts after joining invoice lines. The engine must report/refuse unexpected fan-out for an asserted many-to-one relationship; syntactically valid SQL is not proof of a meaningful total. Empty datasets yield COUNT 0 and unavailable non-count statistics unless a mathematically defined identity is explicitly part of the measure. Percentage formats declare whether source values are fractions or percentage points. Never attach USD to mixed-currency rows simply because a title asks for dollars.

Time is typed as date-only or instant. A date-only due date must not shift with device time zone. An instant view records its display time zone and calendar; month/week bucketing and period comparisons use that declared policy. A series declares its expected time domain/cadence and whether an absent interval means unknown, no event, or an explicit zero from a defined count. Preserve gaps for unknown observations; no smoothing, interpolation or connecting gaps that invents business observations. Expose units and prohibit stacking incompatible currencies/units. Bar axes start at zero unless an explicit justified configuration is visibly communicated. Mixed actual/estimate/forecast data use explicit scope and distinct encodings.

Aggregate marks refer to group identities, not invented record IDs, and never offer direct cell editing. Source-row edits resolve exact current record IDs through the named action. Group drill-down stores the typed query, group key and read snapshot, then resolves contributing rows through a bounded host query. Current grouped results have no per-row inputs; implement this lineage path rather than invent it from display labels. If the source changed, refresh and label the new result or report the stale snapshot; do not silently open current rows as the historical inputs. Frozen visual export and historical chat capture require a new bounded capture result: displayed exact values, definition/query/parameter hashes, source definition versions, complete contributing-version manifests for the displayed measures, and coverage. A current query cursor is not historical evidence: DatasetQueryExecution refuses it after the dataset snapshot changes. Persist verified manifests through existing immutable workbook storage, sharing identical manifests across an overview; never put large input-ID lists into model context or app JavaScript. Capture input identities under the same read snapshot and query-set budget as the values. If capture exceeds its bound, report a noncapturable preview and require a narrower result before publishing a durable visual answer. Current group drill-down rechecks the snapshot; historical inspection opens captured immutable inputs. P1 does not promise a new general as-of SQL engine. Portable copy and deterministic reconstruction must retain these manifests and referenced versions without a parallel ledger.

### State, sharing and persistence

Separate package-owned capabilities, durable presentation, logical view state and per-surface mechanics. Source, declared views, data bindings and business actions belong to the exact reviewed package. Changing those creates a new package version and follows existing review/enable behavior. Ordinary Home placement uses existing versioned space edits.

Presentation-only edits must not recompile or reauthorize the app. Add host-owned `visual_presentation` records using the existing item/version/change-capture machinery, not an independent business-data table or the mutable draft store. These records hold a bounded title/format/layout/filter/annotation override with an explicit owner: `appView(appSpaceID, viewID, contractHash)` or `workbookComponent(spaceID, componentID, contractHash)`. An immutable chat result owns its descriptor in its surface publication, not a fictional app. Saving that standalone result to Home atomically creates a workbook-owned component/preset with the same validated data bindings; an app-backed result instead retains its app-view reference and grant scope. Only metadata is copied, never business rows. Remove/reorder affects placement; delete/archive a preset is explicit and leaves recoverable placeholders for other references. Owner or source removal cannot silently retarget a view. They cannot introduce a dataset, field, join, action, asset or executable expression outside the reviewed descriptor. Every update has an expected record version, mutation receipt and history/recovery; the metadata never contains copied business rows. These typed presentation records are excluded from business datasets and recent-document projections, carry the configuration request/actor provenance, and never masquerade as customer events or calculated business results. The visual evaluator validates overrides again at read time and applies the owner-specific authority to every read. An app-owned preset cannot turn itself into a workbook-owned query to bypass its grant. Register presentation metadata in Item.technicalKinds/hostOwnedKinds and canonical schema/reconstruction validation, write it only through the domain-owned entry point, and exclude it from business projections, recents and default business search/context; explicit presentation inspection/history remains available. A changed source/view contract that invalidates an override reports an incompatible preset, rather than silently remapping columns. Exact schema/public API changes follow the pre-1.0 policy; selected synthetic fixtures can be recreated, with real workbooks preserved.

Title, compatible mark/axis choices, saved parameter values, density and explicitly saved diagram positions use this presentation route. New fields/grouping not exposed by the descriptor require a reviewed descriptor update. Temporary exploration can change declared query parameters without saving. Data edits still go through existing transactional named actions and Undo. Layout/presentation Undo and business-data Undo/Redo must be distinctly named and show the operation they will reverse; adding a Home view must not unexpectedly replace the app's last business-change receipt. The current native app supports one reversible transaction with explicit canUndo/canRedo, not arbitrary selective history reversal. An Undo control on a historical chat receipt must carry its exact expected transaction token/direction and refuse if a different transaction is now reversible. Extend app.undo/app.redo with this host-verified expected token for receipt-bound controls; a generic Undo latest remains a separately labeled action. Recheck before commit. After Undo, the outcome reflects Undone and exposes Redo only when that same reversal is current. A second Undo never performs Redo; presentation Undo must not alter this business history.

Within one workspace window/session, an app's named view has one logical presentation state for active filters and selected records, usable by chat and every explicitly linked rendering. Different windows have independent transient filters/selections; persisted presets and committed business changes propagate through their existing versioned storage. Opening another window does not alter the first. No process-global selection singleton is required. Hover, focus, scrolling and zoom stay local to the particular surface. A separate saved preset creates a distinct presentation-record ID over the same declared view and data, not a new package or new business records. Linked instances of the same preset share logical filter/selection state; independent presets do not. Do not couple unrelated charts merely because they use one dataset. A linked Home view visibly retains its preset/period; “Save a separate view” makes independence explicit. Merely resizing or opening a second window never persists a filter or changes another viewport.

Generalize NativeAppSession's existing table-presentation map and observer registry for visual state. Separate stable state-owner keys from ephemeral work keys. A linked transient state owner is keyed by physical workbook, workspace session/window ID, owner reference, compatible contract hash and preset ID; it retains selection/filter state across ordinary data refreshes. An independent chat exploration additionally includes its surface ID. Query/result-cache keys add resolved package/preset versions, grant epoch, normalized parameters/query and canonical dataset-read snapshot; request generation IDs guard late completion. Do not put dataset revision or filter value into the owner key and inadvertently reset the state on every refresh. A compatible preset edit rebases state with expected-version checks; an incompatible contract or revoked grant invalidates active work. ### 5.1 Chat is a native interaction surface

Do not mix these behaviors under indistinguishable buttons. Recommendations may be labeled with a reason, but do not preselect consequential business values or silently submit a default.

Initial budgets to calibrate in the native spike: at most 40 controls/nodes and 64 KiB of descriptor data per chat surface, within the existing 128,000-byte bound for the entire message payload, including all surfaces, receipts and envelope overhead. Two 64 KiB surfaces therefore cannot both be inlined at their individual maximum; use verified out-of-line capture references or refuse the oversized publication, never truncate JSON. A visual answer initially shows up to eight preview rows or 200 plotted marks, subject to shared data-completeness rules. A row preview states its shown/total or unknown count and opens the full result. A chart exceeding the compact mark budget uses a validated coarser aggregation or a text summary/Expand action; it never silently drops the remaining points, categories or series. These are chat presentation budgets, not limits on the source population. Share exact aggregate evaluation with full views. At most two visible rich result surfaces actively subscribe to data; offscreen/history rows keep lightweight, correctly sized summaries. No hidden app worker starts merely because a message scrolls into view. These two subscriptions count within the eight-active-rich-view budget for the whole window, not an extra budget per conversation. Do not poll all historical cards or rebuild the transcript on every keystroke.

### 5.3 Three representative journeys

**A missing decision.** “Compare these suppliers” already supplies the files. Sevra asks only “Include delivery in the comparison?” with Include delivery and Item price only, plus ordinary typed reply. Choosing one saves a human response linked to that question and continues the comparison. If the user types “Include delivery, but exclude tax,” retain both pieces of input; do not force the response into one enum and discard the qualification.

**A transaction with missing values.** “Record a payment for Acme” resolves the customer and, if needed, shows distinguishable invoice choices. A small form asks only for the remaining amount and payment date; it does not copy values from the last payment. “250 dollars yesterday” can fill the same fields when the invoice establishes the currency, with a visible resolved date. Resolve relative dates against a host-captured request time, locale, calendar and time-zone ID: use explicit workbook/view settings when present, otherwise capture the current system settings for that request. Do not re-resolve yesterday on a later submit/reopen. Ambiguous currency, date order or daylight-saving time requires a specific choice; date-only values remain date-only. The existing operation's review, if required, shows the exact invoice, amount and resulting balance. Save payment invokes the same registered action as the app and returns its real receipt. Editing any effect-bearing field invalidates an older review. Opening the full editor retains the draft and returning retains conversation position.

**A visual answer that becomes a tool.** “Why did sales fall?” produces a concise explanation, a source-linked period chart and a few exception rows. Inspecting one point shows its exact underlying period/records without asking the model to interpret a click. Open current view expands the existing definition at the selected period. Add to Home creates a live reference/preset through the planned presentation operation. The original answer retains the values and period it used; the pinned live view can subsequently change.

These journeys are acceptance scenarios, not a mandatory wizard. If a request supplies everything and already authorizes the operation, execute within existing policy and show the outcome without adding an input form or redundant approval.

### 5.4 Typed publication and execution contracts

Introduce a bounded host-owned `ConversationSurface` contract in Core, with four primary kinds: `question`, `input`, `review` and `result`. Result surfaces reference the shared `VisualDefinition`/named-view contract; input surfaces reference a saved form/action descriptor or a small ad hoc field schema. Compose registered native primitives only. No HTML, Markdown-encoded callbacks, arbitrary JavaScript, expression evaluator, model-supplied file paths or opaque action URL becomes an executable control.

A published surface has a host-minted ID, schema/catalog version, revision, conversation/message identity, origin request/run, purpose, accessible/plain-text fallback, kind-specific content and exact target references. The host resolves its allowed actions. Question options contain IDs and literal values; actions contain registered operation IDs and validated bindings, not code. Published descriptors are schema-validated and immutable; updates publish a new revision with an explicit supersedes link and cannot retroactively change submitted values. Unknown component/catalog versions retain their readable fallback and disable unsupported actions. The message payload stores the immutable publication and later typed receipts; draft storage remains presentation state. Reuse captured `messages`/`message_payloads` and the existing change/reconstruction mechanism rather than adding a parallel durable ledger. A small derived index is acceptable if rebuildable from these records. Surface publications and draft metadata are not new business records or documents; keep them out of business datasets and Home document recents. Classify only submitted business observations through the existing input-evidence path.

Example of a proposed model-authored question body, before host identities and action bindings are attached:

```json
{
  "kind": "question",
  "purpose": "Choose the comparison basis",
  "question": "Include delivery in the comparison?",
  "fields": [{
    "id": "include_delivery",
    "type": "boolean",
    "required": true,
    "label": "Include delivery"
  }],
  "choices": [
    {"id": "include", "label": "Include delivery", "values": {"include_delivery": true}},
    {"id": "exclude", "label": "Item price only", "values": {"include_delivery": false}}
  ],
  "allowTextReply": true
}
```

Use proposed `request_input` as the single narrow terminal input-request tool. It publishes a validated question/input surface and ends that inference segment as needs_input. Extend the existing `finish` result contract with at most two optional, host-validated visual-result references; it still performs ordinary evidence/completion validation. Existing operation receipts generate review/outcome surfaces directly. This avoids a separate generic UI execution tool. Fetch detailed family schemas on demand and include only the needed capability descriptions in each prompt. Host-authored review/outcome controls should be generated from existing operation receipts, not independently invented by the model. Do not add a tool per widget or a separate UI-generation model. Update the tool registry, constrained grammar, prompt policy and tests together, retaining the existing prompt/run/step budgets. Questions/forms should work without loading the mini-app authoring prompt. Record/evidence choices must resolve to real inspected identities; generated labels alone are not proof that a record exists. Result surfaces bind completed query/calculation/source receipts that pass the existing answer-evidence checks. Do not let a visually authoritative chart, balance or outcome introduce model-invented business values.

Classify an interaction before dispatch:

1. **Presentation only:** expand, select, sort, inspect, change a local filter. Resolve locally through the shared view controller without inference; persistent preset edits still use their normal write path.
2. **Structured answer:** persist the human's submitted values and exact question identity, then admit a causally linked agent continuation if reasoning is needed. An answer supplies information; it is not blanket permission to perform a new action.
3. **Known operation:** submit a named business action, review an exact change, navigate or export. Invoke the existing validated dispatcher directly; no model round-trip is needed to reinterpret a known button. Required grants/reviews remain unchanged.

The agent may propose fields or fill a draft from supplied values, but cannot forge a human answer, click-confirmation receipt or local execution grant. A native button event is an explicit human action with its own saved provenance. Host events name the exact surface/revision/control and validate its current role; model text, a dataset value or a deserialized payload alone cannot acquire the trusted-event entry point. Preview never implies commit. Read-only requests can display questions/results and keep ordinary input drafts, but cannot gain write authority through a button or a follow-up answer.

### 5.5 Durable input lifecycle, drafts and recovery

Add an explicit `needs_input` run outcome and surface lifecycle: published/awaiting input, submitted, executing, succeeded, failed, cancelled, superseded or stale. Publish the message, immutable surface, pending-interaction identity and `needs_input` terminal transition in one existing captured database transaction, checking cancellation/current run identity before commit. A failed commit exposes no actionable control. Only a complete, grammar/schema/evidence-validated request_input response reaches that transition. Splash protocol 13 distinguishes successful frontend Stop from user Cancel; neither that transport primitive nor streamed partial JSON is the application-level needs_input terminal. User Stop and Cancel this question retain their existing separate meanings. Release the inference lease only after the durable transition; a crash after commit reopens one pending question without rerunning the model or minting another surface. Do not copy the current separate addMessage/finishAgentRun sequence without this atomic boundary. Do not leave a model/tool call busy indefinitely while the user answers. A submitted answer that requires agent reasoning creates a new admitted run linked to the exact original request and input surface, carrying the original task, completed-operation receipts, restrictions and supplied values. A fully specified known form/action dispatches directly through its existing operation contract and does not start inference. The needs_input run is closed for inference and has an associated pending interaction; it is not an executing background run. Reuse request admission and causal-capture patterns; this is a narrow handoff, not a new workflow scheduler. Waiting/answered/cancelled must be reflected consistently in activity, history, recovery and summaries. Add and test the needs-input status in every terminal-state validator, activity projection and stopped-request/history path; do not merely add a UI badge. Keep request restrictions and completed-operation identities host-owned across the handoff. A reply cannot reset action retry tokens or override the original read-only scope. A separate explicit request to change scope is admitted as new work with its own authority, not smuggled through answer values. If an inference lease is unavailable after the answer is saved, show Answer saved, continuation not started with a specific Retry continuation action; do not lose the answer or secretly schedule background work.

A trusted native submission saves a canonical role=user message with readable supplied values/qualifications and a typed payload linking its exact surface/revision, response identity and original request. It is the original human answer, not an assistant paraphrase or a tool/event-only receipt that readHistoryEvidence cannot cite as something the user said. Admission/receipt and this message share one captured submission boundary. Typed replies reuse their already saved user message rather than duplicating it. Unsent drafts never become human evidence. History references and numeric grounding point back to this original message; a later assistant answer, option label or digest cannot substitute for it. Model tools cannot call the trusted submission entry point. Compaction, parent-thread scope and portable-copy rules still apply.

Give each form an independent draft identity scoped to physical workbook, conversation, surface and definition revision. Reuse Core validation and FormDraftSession behavior where applicable; use the existing app-session revision/validation mechanisms for explicitly shared named-action drafts without treating every empty visual field as a missing chat input; ad hoc questions need no saved business form. Preserve edits across rerender, navigation and restart, detect conflicting window edits, and keep unsent values outside model history/evidence. A model update cannot overwrite a dirty human field. When the composer is explicitly answering a form, its submitted text and any current local field edits must be reconciled by revision, preserving conflicting alternatives rather than guessing. Typed corrections and controls update the same draft after explicit target resolution, with input revisions and expected-version checks. Validate at useful boundaries and on submit; retain original entered text beside parsed exact numbers/dates when needed. No implicit business defaults from an unrelated form/session. A new transaction starts a fresh invocation draft; only an explicit Continue this draft shares its values with an existing mini-app form. Submitted current-request values take precedence over unrelated control drafts. Retain the newer AppOperationContext distinction between named-action inputs and visual drafts.

Extend `claimChatApproval` to accept a trusted native submission naming the exact approval ID/revision and effect digest. Do not implement old-card buttons by injecting the text Confirm into the composer: today's latest-pending lookup can target a different proposal. Typed Confirm remains available only when the host can resolve the intended current review unambiguously; otherwise identify the alternatives. Model tools cannot manufacture this claim.

Submission uses a durable interaction ID and the operation's existing idempotency/receipt mechanism. Separate the response receipt from execution: record once, validate current schema/targets/grants, claim the exact operation once, execute and record the outcome. Validate and claim atomically against expected identities where the current operation supports a transaction; never hold that transaction open across inference or user input. Duplicate clicks, two windows and restart must not execute twice. Typed answers and native submits for the same surface revision must converge on this one claimed identity. If a process stops after a claim with uncertain completion, inspect operation proof before retrying; never announce success from a pressed button or blindly replay. A failure before effects are committed preserves the inputs for an explicit retry; distinguish a retriable execution attempt from the one immutable response identity. Retry uses the established operation identity until its committed outcome is known, so a new attempt ID cannot duplicate business effects. Business-rule refusal requires a user decision; do not automatically change amounts/dates or regenerate the app to make it pass. Stale forms preserve values and offer Refresh review. A cancelled, superseded or interrupted request stays nonactionable until the user explicitly opens a new valid continuation. Missing/withdrawn targets and changed app versions keep the old input readable but require revalidation before a new action. Portable copies retain evidence and unsent drafts but never inherit local grants or replay pending execution; the user explicitly continues against the copy after revalidation.

Cancel this question ends that pending input branch without undoing prior saved work. Decline is a valid structured response indicating that the user will not supply the requested value; it can produce an explanation or a permitted alternative, never a guessed value or repeated prompt loop. Stop cancels currently executing work and reports any already saved effects as the current runtime does. None implies successful completion of the business task. At most eight input groups may remain pending per conversation; additional requests must resolve an old group or finish with a readable unresolved outcome, while ordinary chat remains usable. Ordinary new chat messages stay ordinary requests unless they clearly address the active question. Do not silently attach a reply to a background thread or replay old pending work. Moving to another thread preserves drafts but does not submit them.

### 5.6 Historical answers, live views and native composition

Historical visual answers default to a bounded captured result with exact source/query identity, values, coverage, period and generated-at time. Persist enough to reproduce the displayed result after reopen. Large immutable result payloads use existing workbook-managed evidence/asset storage with verified identity, not inline bytes beyond the message bound. An explicitly exploratory transient view may be live while in use, visibly labeled; later history shows its captured result and an Open current view action. Do not silently refresh old chart numbers beneath an old explanation. Current approval/action status may update from receipts without rewriting the original proposed effect.

Chat selections/filters are local to their surface by default. Open in app carries the chosen context explicitly; it does not silently change the user's saved Home preset. Add to Home creates a live reference/preset only when requested. A deliberately linked preset retains the sharing rules in section 4. Revalidate bindings and authority on live open/refresh/dispatch and reject late results after revoke/version change. Rendering an already published immutable capture uses the host-only historical rule in section 4, with no fresh query or execution authority.

Move only reusable field/visual presentation into `SevraVisualUI`; it depends on Core, the lower-level SevraMedia module for image delivery, and Apple frameworks, never PreviewUI or the app executable. Form session ownership stays in PreviewUI/host adapters; pass narrow picker/navigation/submit closures instead of importing WorkspaceState into shared views. Update ConversationMessageRow equality, WorkspaceSnapshot and the content cache to include surface/receipt/draft revisions as appropriate; a body-only equality check must not hide a changed form or approval. Current readConversationWindow selects at most 100 messages within 2 MiB of bodies; WorkspaceSnapshot has no general payload projection, although historySlice already retrieves bounded payloads. Extend the coherent window read to budget bodies plus summary descriptors together within 2 MiB. Preserve the requested anchor and existing pagination behavior. Hydrate at most two visible result messages and one active input group on demand, each within the existing 128,000-byte message-payload bound and its 64 KiB per-surface bound; cancel obsolete hydration and check message/payload revisions before display. Original-message navigation restores its own payload; bring-to-main/share-summary remains a reference with readable text and an exact origin link, not a cloned actionable form or renewed approval. Agent history projects bounded references/supplied text, never image bytes or every historical descriptor. Preserve measured row heights and reading anchors when mounting rich results; no auto-scroll while the user reads older history. New streamed output cannot steal focus or replace an active field. Fully validate a control group before enabling it; do not execute partial streamed descriptors. Multiline fields, Tab/Shift-Tab, Escape and submit shortcuts keep native semantics, with no global Return handler that both submits a form and sends the composer.

Every surface has a readable fallback for copying, history search, export and unsupported clients: question/options, submitted values, effect/result and source links. Compact agent history includes submitted structured answers, receipts and the bounded currently pending question, never draft keystrokes or entire UI trees. Untrusted labels/evidence remain data. A stored historical choice must not return as a fresh user instruction or renewed authority.

## 6. Technology choices and open gates

For inline chat, use the existing native message renderer plus the small Core surface schema in section 5. Reuse field/visual components and existing business dispatchers. A2UI, Slack Block Kit, MCP elicitation and Adaptive Cards provide useful catalog/action/lifecycle precedents, documented in [[records/research/inline-chat-interactions]]. Adopting their SDKs, transport or full specifications is not necessary. There is no new hosted service, subscription, network dependency or per-widget code generation in this design.

Use Swift Charts on the existing macOS 14 baseline. Apple documents marks, axes/legends, selection and scrolling; current Home already imports Charts. NSHostingView is the supported bridge to AppKit. Keep newer 3D/vectorized APIs out of baseline requirements. This is a proposed integration, not a claim that embedding is already qualified in Sevra.

Use a finite visualization grammar inspired by declarative systems such as Vega-Lite, without shipping its web renderer or cloning its entire language. Retain the native SDK and sandbox. Browser-hosted Vega/ECharts could increase chart variety quickly but would introduce a second UI/input/accessibility and export stack; that tradeoff is not justified for the accepted native direction.

For diagrams, prefer a proven layout engine over model-written coordinates or an unbounded homegrown graph-layout project. ELK.js is the first spike candidate: bundle a pinned layout-only build as a host-owned resource in an isolated worker context, then render resulting geometry natively. Its documented browser/Node support is not evidence that it fits Sevra's QuickJS restrictions. Measure compatibility, initialization, memory, time, cancellation, cyclic graphs, stable ordering, resource signing and license/notice delivery. Do not silently relax existing app execution limits to accommodate it. Graphviz dot is the fallback comparison candidate; evaluate embedded library packaging and dependency/resource costs before selecting it. No external dot installation or shell tool is a user prerequisite. For either candidate, the host supplies measured native label sizes, stable sorted IDs, explicit direction and a fixed supported algorithm/seed. Layout results are cached by graph content, text metrics, options and engine version, not by transient screen coordinates. Ordinary data refresh must not reshuffle unchanged nodes; fit/zoom and saved manual positions remain explicit. The worker receives only validated graph data and returns validated finite geometry. Nodes/edges use stable IDs; endpoints must resolve, self-loops/cycles and collapsed groups have defined representations, and missing external dependencies or clipped subgraphs are explicitly marked. Layout may not imply the displayed graph is complete when node/edge limits truncate its source. Native pointer hit regions, keyboard order and text labels must remain consistent after zoom/collapse. Saved manual positions are keyed to compatible node identities and may not silently override new required edges or labels. It cannot resolve asset paths, open URLs or widen app authority.

If neither candidate clears the gate, keep general diagrams explicitly unavailable and deliver a narrowly specified native hierarchy/process view only if it has its own acceptance.
