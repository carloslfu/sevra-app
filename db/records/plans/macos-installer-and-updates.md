# Standalone macOS installer and updates

**Status** Proposed implementation plan. Sevra currently ships as a source preview. The native packager builds `Sevra Native Preview.app` with ad-hoc signing. GitHub Releases had no published binary at the time of this review. This plan covers a standalone Mac download, in-app updates and the path from a possible early-access build to the first company-signed public release.

## Distribution design

| Decision | Proposed release behavior |
| --- | --- |
| Manual install | One Apple Silicon `.dmg` containing `Sevra.app` and an Applications shortcut. The same finalized DMG is the full Sparkle update. |
| Download hosting | Versioned assets on [GitHub Releases](https://github.com/carloslfu/sevra-app/releases). A website download button and the README link directly to the current verified stable DMG. |
| Update discovery | Sparkle 2 reads a static, signed HTTPS appcast at the proposed `https://www.sevrahq.com/updates/macos/appcast.xml`. The feed links to exact GitHub release assets. An appcast is the XML list of available versions, downloads and signatures. |
| Identity | Proposed public bundle ID `com.sevrahq.sevra`, with app name `Sevra.app`. Confirm it on the target team before the first externally distributed installer and keep it across releases. It is distinct from the two existing source-build IDs. |
| Launch order | Rehearse packaging and updates while Apple enrollment is pending. An optional ad-hoc early-access installer uses the public bundle ID, feed and Sparkle key from its first build. The public stable release uses company Developer ID signing and Apple notarization. Stable release readiness depends on the signed candidate and live update checks. |
| Network | Initial download, optional model setup and update checks use the network. Import, search, workbook operations and configured local inference remain available offline. Sparkle system profiling stays disabled. The feed host and GitHub receive ordinary download requests. |

GitHub hosts immutable versioned bytes and the website controls which version Sparkle offers. Keep the feed URL permanent and serve the XML as a static file through the existing site. This uses the current website and public source repository as independent release components. [Sparkle publishing](https://sparkle-project.org/documentation/publishing/) · [GitHub release links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)

## 1. Build an installable app

- [ ] Extend the existing native SwiftPM build and Python staging script with an explicit release mode. Build from a clean commit and pinned Xcode, Swift, Rust, Sparkle and upstream native inputs. Generate the final Info.plist before signing. Set Apple Silicon and macOS 26.4+ for the candidate, then publish the hardware, OS, memory and disk requirements actually qualified on the released build. Use the corresponding OS minimum in the bundle and appcast. Sparkle's architecture filter can distinguish arm64 from Intel, so Sevra must still check its M3-or-newer runtime floor in setup. Keep the build/catalog variants and public app distinguishable. [Existing native packager](../../../scripts/package_native.py) · [[records/specs/distribution]]
- [ ] Stage the main executable, parser, sandboxed worker, Splash helper, Metal resources, grammar library, resource bundles, licenses and Sparkle framework and helpers inside the app. Use bundle-relative paths and verify runtime loads on a supported Mac with only the downloaded app. Record minimum OS, executable architecture, bundle ID, version and build in the release receipt. Restore and check `.sevra` and `.sevraz` Finder associations for the public app. Display app and build versions in About Sevra.
- [ ] Include the matching `sevra` CLI inside the signed bundle with its resources and helpers. Document its exact bundled path and offer optional, explicit CLI linking after installation. Reuse the source installer's collision checks for the link, and verify a link to the public app still resolves after an in-place update. A drag install consists of the app copy only. [Existing CLI installation](../../../scripts/install.sh) · [[records/operations/build-and-run]]
- [ ] Package a compressed, read-only disk image with the app and an Applications shortcut. Confirm the downloaded image mounts, copies with permissions and framework symlinks intact, and can be ejected before first launch. Download the model separately in the app and keep build tools on the build Mac. Keep each release asset below GitHub's 2 GiB limit. [Apple distribution packaging](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution) · [GitHub release asset limits](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas)

**Versioning.** Derive `CFBundleShortVersionString` from the three-part release version and provision a strictly increasing numeric `CFBundleVersion` across every release on a public feed, including previews and hotfixes. Store both with the release's source commit and tag. The appcast uses the same build and displayed version. A preview tag can be `v0.9.0-preview.1` while About shows `0.9.0` and identifies the preview. The first stable build must have a higher build number than every supported preview. Fail preparation if a tag targets a different commit or the build number would collide. [Apple version format](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring) · [Sparkle version ordering](https://sparkle-project.org/documentation/publishing/#internal-build-numbers)

## 2. Integrate Sparkle and preserve local data

- [ ] Pin a supported stable Sparkle release and use matching packaging/signing tools. Embed the versioned framework with its symlinks and executable permissions. Resolve it via the app's Frameworks directory and sign its retained nested components. Configure XPC services for the host app's actual sandbox status. Keep Sevra's separately sandboxed worker and its entitlements intact. [Sparkle integration](https://sparkle-project.org/documentation/)
- [ ] Use a single `SPUStandardUpdaterController` with the native **Sevra → Check for Updates…** menu and a Settings switch for automatic checks. Leave `SUEnableAutomaticChecks` unset for Sparkle's second-launch opt-in. Users explicitly install updates in the initial policy. Set `SUAllowsAutomaticUpdates` and `SUEnableSystemProfiling` to false. Use Sparkle's preference state and expose actionable messages for offline checks, up-to-date and incompatible versions, denied access, and a copy launched from the DMG or another read-only location. Keep downloads authenticated by Sparkle and use the normal OS authorization flow when needed. [SwiftUI updater setup](https://sparkle-project.org/documentation/programmatic-setup/) · [Sparkle configuration keys](https://sparkle-project.org/documentation/customization/)
- [ ] Keep the app replacement separate from user data. Ensure the existing quit path can postpone installation while a workbook write, export, inference job or model download needs to finish or be cancelled safely. Use Sparkle's installer and relaunch path. Verify workbook packages and included files, changes, recents, preferences, approvals, and compatible installed models before and after update. Keep models and preferences outside the bundle. Use the existing pre-1.0 policy for earlier development formats. At the first supported release, record the workbook schema/API baseline and test direct upgrades from older supported builds, including users who skipped versions. Verify a backup and interruption-safe migration before shipping any update that changes supported data formats. [[records/specs/distribution]] · [[records/specs/persistence-readiness]]
- [ ] Generate Sparkle's EdDSA key once for the public app and embed `SUPublicEDKey` and `SUFeedURL`. Use a separate key and feed for disposable QA. Sign each finished DMG, and sign the appcast with embedded release notes for the shipped version. Enable `SUVerifyUpdateBeforeExtraction` and `SURequireSignedFeed`; set `SUSignedFeedFailureExpirationInterval` to `0` so feed validation failures require repair or a verified manual replacement. Keep full DMG updates initially and verify both download and feed signatures. Preserve the public key across the first Apple-signing change. [Sparkle signing and key rotation](https://sparkle-project.org/documentation/#rotating-signing-keys) · [Sparkle signed feed settings](https://sparkle-project.org/documentation/customization/#security-settings)

## 3. Rehearse before Apple approval

- [ ] Build two distinct ad-hoc QA installers with monotonically increasing build numbers. Use a separate HTTPS QA feed and disposable data. Test a standard browser download, the drag install, first launch, model setup, and a real Sparkle update from the older installed copy. Confirm an empty signed feed gives a normal no-update result. If the ad-hoc host cannot load the framework with library validation enabled, resolve that in the QA build configuration and verify library validation in the Developer ID build. Include a bad-signature control and an interrupted or offline download.
- [ ] Decide whether to distribute an early-access DMG. If selected, start from the production-shaped app, include the production key and feed, and publish it as a clearly labeled GitHub prerelease. The stable feed can start with a signed empty appcast. If distributing subsequent early-access updates, use a named `early-access` appcast channel with opt-in confined to those builds. Stable clients use the default channel, and early-access clients can also receive default-channel releases. Verify feed/key continuity before handing out the first preview. Keep the preview and the signed handoff on a compatible workbook format. If a breaking development change intervenes, keep affected builds on a documented export or manual handoff until compatibility is proven.
- [ ] Give early-access users exact first-launch instructions. Download the official GitHub DMG, drag Sevra to Applications, launch the copy, and if macOS blocks that known download use **System Settings → Privacy & Security → Open Anyway** for Sevra. Some managed Macs disallow the exception. Those users need the signed release and any permissions required by their administrator. Verify the sequence with a tester. Earlier source installs have no in-app updater. Their entry path is to install the signed app once and reopen compatible existing workbooks. Avoid overwriting either existing development app or changing its CLI link implicitly. [Apple's Gatekeeper instructions](https://support.apple.com/en-us/102445) · [Sparkle channels](https://sparkle-project.org/documentation/publishing/#channels)

Sparkle's validator accepts a changed Apple code-signing identity when the old app trusts the EdDSA signature on the new archive and the new app's code signature validates. Keep the same public bundle ID, app name, feed and EdDSA key at the handoff. Keep the signed build number above the preview. To test the final DMG before publishing, point a release-equivalent predecessor at a staging URL and sign that staging feed with the same key it already trusts. Keep the candidate's production feed URL and bytes intact. Rehearse with ad-hoc and signed predecessors, then check the live production feed from an actual shipped preview if one exists. The preview may need to request microphone access again after the Apple identity changes. Offer downloading and replacing the app manually as a recovery path. [Sparkle validator](https://github.com/sparkle-project/Sparkle/blob/2.10.1/Sparkle/SUUpdateValidator.m#L274-L345) · [Apple code identity and permissions](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements/)

## 4. Sign, notarize and verify the candidate

- [ ] After Apple organization enrollment, provision the team's **Developer ID Application** identity and notarization credentials. A DMG with an app uses the Application identity. Record the expected Team ID and certificate fingerprint. Use a trusted release Mac with the signing keys in Keychain for the first release. Keep the Apple certificate private key, notarization credentials and the Sparkle private key distinct, out of the repo and build logs. Keep a protected, recoverable backup of the Sparkle key and signing identity and verify restore with the public key or certificate fingerprint. [Developer ID certificates](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/)
- [ ] Verify raw upstream engine and grammar bytes against their pins before staging. Sign nested executables, frameworks, and helper bundles from the inside out, including the bundled CLI copies. Preserve the sandboxed worker's entitlements. Apply hardened runtime, the required resource entitlements for dictation, a secure timestamp and the release team's signatures as appropriate. Leave ordinary resources such as Metal libraries as sealed resources. After signing the leaf binaries, generate the app and CLI runtime manifests from the final signed bytes. Preserve upstream pins separately and seal the outer app after finalizing manifests. The current runtime verifies the engine and grammar digests, and blanket re-signing invalidates those comparisons. [Sevra runtime verification](../../../Sources/SevraProduct/NativeProductResources.swift) · [Apple distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac) · [Hardened runtime](https://developer.apple.com/documentation/xcode/configuring-the-hardened-runtime)
- [ ] Create and Developer ID sign the DMG. Submit the final container with `xcrun notarytool submit` using the stored credential profile, wait for an accepted result and inspect the notary log. Staple and validate the ticket on the DMG. Verify app and nested signatures, expected Team ID, runtime flags and worker entitlements with `codesign`. Use `--deep` for verification only and assess the installed app with a real Gatekeeper-protected fresh launch. Rehearse offline first launch after obtaining the stapled DMG. If the copied app needs a stapled ticket of its own, notarize and staple the app before rebuilding, signing and notarizing the final DMG. Use Apple diagnostics to resolve any failed check before uploading. Timestamp, notarize and staple before computing the final artifact checksum and Sparkle signatures. Treat the resulting bytes as immutable. [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow) · [Apple's fresh and upgrade test cases](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution#Test-your-distributed-product)

## 5. Publish and maintain each release

1. **Qualify the exact source and candidate.** Run `scripts/check.sh` and the relevant hosted checks at the release milestone. On the release Mac produce the final DMG, a SHA-256 checksum, and a receipt with source commit/tag, version/build, asset size/digest, Team ID and notary submission status. Complete the pre-publish rows of the verification matrix below. Reuse the candidate bytes tested. The public release's first install and a future updater rehearsal require separate evidence.
2. **Upload to a draft.** Create or verify the release tag at the tested commit. Upload `Sevra-<release-version>-macOS-arm64.dmg` including any preview suffix and a SHA-256 checksum file to a GitHub draft. Write release notes with requirements, changes, known limits, workbook format implications and install/update steps. Verify the draft assets round-trip to the same bytes. If repository immutable releases are enabled, finish attaching all assets before publishing. Keep prerelease tags marked as prereleases. [GitHub release management](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository) · [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
3. **Publish binary, then advertise.** Publish the GitHub release first. Verify that an anonymous request to the exact versioned GitHub URL follows redirects and yields the expected size, SHA-256 and DMG. Build the appcast with Sparkle's matching `generate_appcast`/`sign_update` tools. Ensure the item uses the exact public asset URL, `sparkle:version`, `sparkle:shortVersionString`, `sparkle:minimumSystemVersion`, arm64 requirement, length, EdDSA signature and release notes. Sign the final XML bytes after its URLs and content are complete. Commit the signed XML to the website's static public files and deploy it with a short cache lifetime. Verify that the endpoint returns XML, preserves the signed bytes, and retains known-good entries when the site changes. Keep previous entries for still-supported OS versions where needed. Check stable eligibility before exposing any preview entries. [Sparkle appcast format](https://sparkle-project.org/documentation/publishing/)
4. **Update the website and README.** Point the public CTA and source README at the same verified stable download and release notes. Document the Apple Silicon, OS and memory requirements, model size plus free working space, model setup and retry, offline use, **Check for Updates…** and getting help. Show download size and tested limitations. Keep the source-build path available for contributors. Use the customer instructions below for the install, initial setup and manual replacement. For help, ask for version/build, Mac chip, macOS and the exact error, with workbook and personal data omitted.
5. **Verify live and record the result.** Download through the actual CTA, launch and complete a starter workbook on a supported Mac. Check eligibility and upgrade from an already installed build through the actual live feed. Open the sample workbook and confirm the new About build, preserved edits and working model. Retain checked versions and receipt links. Move repeatable packaging/checks into a manually dispatched release workflow only after the local signed path is repeatable. Use a trusted ARM runner and verified toolchain for builds, and keep physical M3-or-newer runtime qualification separate. Restrict release jobs to a trusted commit and a protected release environment, isolate secrets from pull-request jobs, use a temporary signing keychain, pin Actions to full commit SHAs, serialize publish jobs and grant GitHub release write permission only to the publisher. [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use) Treat tag creation, packaging, and production feed promotion as distinct steps.

## Customer instructions to validate

1. **Install.** Check the Mac requirements, download the DMG, open it and drag **Sevra** to **Applications**. Eject the image and open the installed copy from Finder. A standard account that cannot write to the shared Applications folder can use its own `~/Applications` if that path passes the install and update checks.
2. **Start a workbook.** Import a file or open a workbook immediately. To use local AI, go to **Settings → Download model** or **Use existing model files…**. The initial model download needs internet access and the published free disk space. Leave the model in its separate location across updates.
3. **Update.** Choose **Sevra → Check for Updates…**, review the release notes and install when ready to close the app. Let Sevra finish any active work, then reopen and check **About Sevra**. Automatic checks are optional.
4. **Replace manually when needed.** Quit Sevra, download the current signed DMG from the website, and replace the matching installed app in the same Applications folder. Keep workbooks and the model directory in place. If coming from an old source preview under a different name, install the public app alongside it and open a compatible workbook from Finder.

## Verification matrix

| Check | Evidence required before advertising the release |
| --- | --- |
| Fresh install | Browser download on a clean supported Mac without developer tools, valid quarantine and Gatekeeper, drag to Applications, eject, launch from Finder, open `.sevra`/`.sevraz`, work without a model, optional model download and one offline inference after setup. Test a standard account and a writable per-user Applications location when relevant. |
| Supported hardware | Check the oldest advertised macOS and the newest supported version available for testing, plus each advertised memory tier. Test setup/refusal for unsupported OS, M-series generation and insufficient free space. Report exact chips, memory and OS tested. |
| Real upgrades | QA ad-hoc to newer ad-hoc, ad-hoc to Developer ID if offering early access, and a signed-to-signed rehearsal. Test manual check, scheduled-check preference, quit/relaunch, build number increment, preserved workbook edits, recents, approvals, optional CLI symlink, extraction, dictation and model reuse. Test repeat check after update and at least one skipped build once available. |
| Validation and recovery | Bad DMG signature, modified feed, missing or truncated asset, equal/lower build, wrong channel, incompatible OS and dropped connection all leave the previous install usable. Exercise cancellation, a read-only launch path, insufficient space or denied replacement, and rerun a valid update afterward. Check that a workbook write completes or is safely deferred before relaunch. |
| Live delivery | The website and README download the same signed/stapled asset. Public XML matches the signed file. GitHub asset bytes match the release receipt. An applicable installed copy sees the right version and stable builds see only eligible stable updates. A manual replace opens the same data. |

## Recovery and ownership

- **A bad update.** Remove the affected item from the feed, re-sign and deploy the feed, then point the public download to a verified build suitable for fresh installs. Removing an offer stops new discoveries after caches refresh. A client may already have downloaded it. For users who received it, ship a fixed build with a higher build number. Validate data compatibility before recommending a manual downgrade. For a release with schema changes, recover using the corresponding backup and a documented compatible build. Keep exact known-good installers and release receipts.
- **Feed or hosting outage.** The installed app remains usable offline with configured local features. Repair the feed at the existing URL. Direct users to the verified GitHub release for a normal manual replacement. Keep the previous signed feed and artifact URLs available for recovery. Publish feed and release notes from reviewed bytes and verify serving across website deployments.
- **Signing incident.** For suspected Apple key exposure, contact Apple, follow the certificate revocation/reissue path, and validate a new build with the same Sparkle public key. For suspected Sparkle key exposure, pause promotion, protect the feed origin and publish explicit signed-installer recovery instructions. For a lost key, recover from the protected backup, or use a verified Developer ID–signed manual replacement with a new Sparkle key. Any planned key rotation needs an end-to-end test and one unchanged trust mechanism. [Apple certificate guidance](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/) · [Sparkle key rotation](https://sparkle-project.org/documentation/#rotating-signing-keys)
- **Owners.** The app release maintainer owns builds, keys, notarization, GitHub assets and release receipts. The website maintainer owns the permanent feed endpoint, deploy and download CTA. The release reviewer confirms the live install/update paths and data preservation. A single person can hold all three roles.

## Release order

1. Build and rehearse the full installer and updater before Apple approval.
2. If early access is useful, ship the verified ad-hoc preview to a small cohort with the updater already enabled for the bridge.
3. After enrollment, verify the signed DMG on a clean Mac and prove the bridge if a preview shipped.
4. Publish the signed download and recoverable update path. Keep the same process for subsequent versions.
