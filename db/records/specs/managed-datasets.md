# Managed datasets and replayable storage

Adopted direction, October 28, 2026. Owner authority:
[[sources/notes/2026/10/managed-datasets-replayable-storage]]. This extends
[[records/specs/storage]] and [[records/specs/persistence-readiness]].
The target is required implementation work; adoption does not mean it is built.

## Decision and current state

Use one workbook SQLite database with reserved system tables and one managed
native current-state table per structured dataset. Keep shared immutable
Sources/Records, exact lineage, versioned definitions and the existing
committed_changes foundation. Sources and Records describe semantics independently
of physical table layout. File assets remain ordinary files under assets/ unless
explicitly linked.

At checkpoint cd5f854, structured rows still use datasets, dataset_rows, heads and
items.data JSON. Schema-10 complete change capture and inert local reconstruction
are implemented for the fixed canonical schema. Home/space edits reuse them.
Native dataset tables, their registry, schema reconstruction and index management
are not yet implemented. Historical receipts remain valid for their recorded scope.

## Managed storage contract

M01. Reserve the system schema for identity, immutable versions, lineage, assets,
conversation, definitions, receipts and committed changes. A core-owned catalog
registers each dataset, stable column/row identities, logical types, schema version,
formula/dependency bindings, current storage mapping and declared constraints.
Native table/column names are generated by the core from validated identities;
user labels are metadata. Renaming a dataset or column does not break references.
Use the existing core names where useful; a global prefix rename is not required.

M02. A native dataset table is a current-state projection for structured work,
including imported, directly created or AI-proposed accepted working tables.
Rows reference stable logical Record IDs and exact immutable version IDs. Dataset
membership and order remain explicit, independent of query sort or physical rowid.
Two spaces showing one dataset share its data. A saved query/view does not create
another canonical dataset unless the user requests a durable derived result.

A worksheet may contain sparse cells, multiple blocks, mixed types, notes and
formulas. Preserve that sheet/cell structure in its appropriate versioned model;
convert identified structured regions into datasets according to contextual intent.
Reference/analysis-only intake does not silently create native working tables.
No second shared-JSON working-table backend is a long-term product choice. Existing
JSON remains useful for immutable payloads and flexible metadata.

M03. Immutable row versions and versioned dataset definitions, retained by the shared
committed-change history, are authoritative. Native current tables are rebuildable
query projections. App, CLI and local-agent writes use one managed command path,
which validates the exact base, records canonical versions/lineage, updates heads
and native rows, and publishes the receipt and captured changes in one transaction.
A failure rolls back the whole logical operation. A repeated token with the same
payload returns the original result; changed payload or stale base refuses.
Multi-batch imports preserve explicit committed prefixes and resumable identity.
No direct projection edit can become unrecorded authoritative state.

M04. Extend the existing capture/apply/verify contract and schema classification.
Do not introduce a second history ledger for datasets, indexes or workflows.
Declare each table as reserved authority, managed projection, disposable index or
other already supported state class. Registered tables participate in integrity,
closure, export/reopen and reconstruction; unknown structures fail validation.
A valid managed schema is validated against trusted registry definitions, instead
of exempting all dynamic tables from the current exact-schema guard.

The first implementation may capture managed row images within the same history
for exact reconstruction. Their role remains a projection, not independent truth.
Qualify independent projection rebuilding from retained canonical row versions and
definitions as well. Future elision of redundant captured projections is an
optimization requiring evidence, not a prerequisite or permission to discard history.

M05. Logical schema changes are versioned, recorded data: create dataset, add/rename
column, change logical type/formula/constraint, archive/remove a column or dataset,
and restore a previous definition. Keep exact previous/resulting schema versions,
IDs, source/actor and affected row versions. Preserve removed values in history.
History within a workbook remains required even before production 1.0.

Record schema definitions in the same committed-change foundation. Trusted core
code materializes their physical tables/columns/indexes before dependent row changes
are applied. A row-image log alone cannot reconstruct CREATE/ALTER operations.
Specify and test transaction ordering for catalog changes, physical DDL and row
images, including edits that rebuild a physical table. Unknown definition/change
versions refuse without partial publication. Never execute SQL supplied by a model,
imported workbook or historical payload. Replay restores saved identities, values
and times without model inference, parsing, external reads or tool execution.

M06. Choose native storage from explicit logical types and exact value semantics.
Preserve text identifiers/leading zeros, null versus empty, booleans, dates and
original lexical values. Keep Decimal precision/rounding and units; ordinary REAL
must not silently replace financial decimals. Mixed spreadsheet cells and formula
errors remain representable through declared flexible values/cell metadata.
Inference cannot destructively coerce values. Type changes validate all affected
values with explicit failure or reviewed conversion and preserved originals.
Formulas, dependencies, source coordinates, cached results and calculation status
are distinct. A cached value is never claimed as a live formula.

M07. Managed queries compile typed filters, joins, grouping, aggregates and sorting
against registered datasets/columns with parameterized values. Bound result size,
work, memory and cancellation; page/virtualize rows. Views share the managed query
contract. Index underlying physical tables, not ordinary SQL views. Add ordinary,
composite or partial indexes for demonstrated access paths. Index recommendations
from AI go through a core policy, validated column IDs, query-plan checks and storage/
write-cost bounds. Do not create every conceivable index automatically.

Semantic uniqueness/relationships belong to versioned logical definitions and are
validated before acceptance. Pure performance indexes and FTS are disposable local
projections; their exact physical choice/order is not shared business authority.
Retained text/locators and canonical values rebuild them without rereading external
sources. Search results still resolve exact record versions and disclose coverage.

M08. Agents/harnesses request managed create/edit/query/index operations. The core
owns DDL and reserved tables. Keep current request scope, proposal/review boundaries,
stale-base refusal, exact receipts and shared native/CLI semantics. Exposing index
management must not expose unrestricted SQL, schema edits to system tables or new
acceptance privileges. Publish only implemented commands in the CLI skill.
Users choose work, data and meaning, never physical storage or index layouts.

M09. Preserve globally unique workbook/entity/version/operation identities and
explicit predecessor/schema dependencies. New dataset references use stable logical
keys. Physical SQLite rowids, local counters, wall-clock order and user-facing names
must not become cross-device identities. The existing fixed-schema, single-chain
row-image replay remains scoped local reconstruction. Its physical-rowid coupling
and single-predecessor assumptions are recorded future replication constraints.
This slice must not claim that exchanging those payloads merges concurrent replicas.

Keep enough exact values, schema dependencies, actors and decision evidence for
future replication and semantic resolution, with corrections/withdrawals/deletes
preserved. Transport, accounts, replica coordination, multi-writer branch ingestion,
conflict resolution and distributed effect execution remain outside current scope.
Retaining evidence or replaying it never grants authority or repeats an external
business effect. E19 must reuse this commit foundation.

M10. Declare supported dataset width, SQLite column/variable/function-argument
limits and capture bounds. Wide or sparse spreadsheets must retain their source
and truthful conversion limits; native tables do not promise unlimited columns.
Keep the current transaction limits visible and benchmark representative work
before claiming faster queries or larger supported datasets. Native tables add
schema management, retained-history/projection storage and write amplification.
Pre-1.0 changes update canonical schemas and recreate selected disposable fixtures;
no legacy development migration/backfill is required. Never silently delete user
workbooks or originals. Supported production compatibility starts at the milestone
in [[records/specs/distribution]].

## Implementation order

Finish any coherent in-flight checkpoint, then implement this storage foundation
before extending dependent E2/E3 dataset/action/workflow persistence. Independent
UI work may continue. Integrate it as E0-D in [[records/specs/native-app-engine]].

1. Inventory existing row identity, membership/order, versions, queries, formulas,
   imports, effects and capture paths. Record mappings and the authoritative state.
2. Build the managed catalog, trusted schema materializer and atomic capture/apply
   lifecycle together. Prove schema-plus-data reconstruction before exposing DDL.
3. Route existing table creation, edits, review, CSV/XLSX conversion, append/replace/
   merge, Undo/redo and native/CLI/model reads through the managed storage contract.
4. Add measured indexes/query paths, projection rebuilds and scoped performance
   evidence; update skill/installation docs only for delivered behavior. Resume E2/E3.

This is a staged implementation of one target architecture. It is not a permanent
choice between two editable storage backends. Original-file evidence and flexible
sheet/cell representations retain their separate purposes.

## Acceptance

MJ01. Create two structured datasets and inspect distinct registered physical tables.
Two views of one dataset share identity/current state. CSV conversion and AI-proposed
creation use the same core; reference/analysis-only intake creates no working table.
Stable IDs, lineage and exact versions survive rename, sort, edits and reopen.

MJ02. Reconstruct into fresh current-format storage after dataset creation, column
addition/rename/type change, formula/constraint change, removal/archive and restore.
Recreate schemas before dependent data; compare current values, history, definitions,
references and effects. Include a physical-table rebuild and unknown-definition
refusal. Model/extraction/external execution adapters are unavailable.

MJ03. In an isolated fixture, rebuild native projections and indexes solely from
retained canonical definitions/versions. Compare current data, types, ordering,
formula state, exact lineage and query results. No reimport or regeneration fills
gaps. Missing authority refuses; a modified projection is detected/rebuilt honestly.

MJ04. Inject failures between catalog update, DDL, canonical row write, projection
write and change publication. Nothing partial commits. Exercise cancel/resume,
changed-token refusal, duplicate retry and competing app/CLI writers. Undo and redo
retain evidence and avoid duplicate inventory effects. Portable export/reopen and
reconstruction preserve historical assets and unresolved explicit links.

MJ05. Prove index use with query plans and measured range/sort/join/group workloads
on representative small and large synthetic datasets. Compare correctness and
resource use with the recorded shared-storage baseline where available. Record
import/query/edit/rebuild latency, database/index/history size and peak memory;
state hardware, fixture size and bounds. An index's existence alone is not proof
that a query uses it. Failed/slow cases remain evidence.

MJ06. Preserve leading-zero identifiers, null/empty, Unicode, exact decimal values,
mixed cells, invalid dates, formula errors and stale caches. Test declared width
and capture limits without partial or silently truncated conversion. Exercise sparse/multiple
Excel regions without forced rectangular conversion. Existing IJ formula/continuity
gates remain open until independently qualified; physical storage does not prove them.

MJ07. Reject raw-model DDL, unregistered table/index objects, malicious identifiers,
reserved-schema edits, invalid types/constraints and schema changes against stale
bases. Managed create/index permissions do not widen business-effect acceptance.
Historical instructions remain inert during reconstruction. Validate app/CLI/model
scope and one nearby refusal case for each newly exposed operation.

MJ08. Extend [[records/operations/persistence-coverage]] and FJ01-FJ06 for every new
durable family and schema operation. Retain actual failing attempts and scope passing
receipts. Local current-format reconstruction is the gate; no live sync service or
two communicating replicas are required. Full release checks remain separate.

## Design review and rationale

First pass, product fit: native columns and relationships fit structured business
work. Flexible sheet/cell data, contextual roles and immutable original assets prevent
an import from being forced into the wrong representation.

Second pass, integrity: authoritative versions/definitions plus one transactional
write path prevent independent editable copies. Schema creation is replayed through
trusted materialization, not omitted from row capture. Logical IDs survive rename,
reordering and physical rebuild. The registry extends rather than bypasses validation.

Third pass, replication and cost: exact local replay is useful preparation but does
not solve concurrent histories, semantic conflicts or duplicate external effects.
Keep those limits explicit. Measure history duplication, schema-change cost and
query plans; do not promise automatic speedups from a different physical layout.

Primary mechanisms: [SQLite transactions](https://www.sqlite.org/transactional.html),
[partial indexes](https://www.sqlite.org/partialindex.html),
[expression indexes](https://www.sqlite.org/expridx.html) and
[changeset schema/conflict requirements](https://www.sqlite.org/sessionintro.html).
These support the mechanism choices, not a claim of measured Sevra performance or
selection of SQLite Session as a replacement for the current persistence layer.
