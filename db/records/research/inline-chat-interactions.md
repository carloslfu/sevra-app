## First-principles conclusion

Conversation is good at expressing intent and ambiguity; controls are good at choosing known alternatives, supplying exact structured values and inspecting results. A useful chat surface combines both without making the user repeat information or navigate to a form for every missing value. The unit to optimize is the completed task with retained context, not the number of messages or widgets.

Use native controls as concise representations of the same typed operation. Do not embed a complete mini app after every reply, generate fresh code for every question, or route deterministic button clicks through another model interpretation. Shared components should adapt to the chat surface. Historical results need stable evidence, while live app/Home views need current data; sharing a renderer does not make their update policy identical.

## Primary sources and transfer decisions

Consulted November 15, 2026. These patterns inform Sevra's design; they do not prove its UX or require adopting another protocol.

1. [A2UI overview](https://a2ui.org/concepts/overview/) describes catalog-constrained UI rendered by client-native widgets. [Actions and functions](https://a2ui.org/concepts/actions-and-functions/) distinguishes agent events from registered operations that do not require a new agent turn. Borrow this separation and catalog validation. No A2UI SDK/runtime or interoperability commitment is needed for Sevra's first increment.
2. [Slack Block Kit](https://docs.slack.dev/block-kit/) reuses structured blocks across messages, Home and modal surfaces. Its [button schema](https://docs.slack.dev/reference/block-kit/block-elements/button-element/) gives an action its own identifier. Borrow shared primitives with surface-specific composition and explicit event identities; do not copy Slack's surface sizes, cloud interaction transport or feature limits.
3. [MCP elicitation, version 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation) defines structured form input and distinct accept/decline/cancel outcomes, with client control over presentation. Borrow explicit response states and reviewable input. This is a deliberately versioned reference, not a claim that Sevra implements MCP elicitation or that this is the latest protocol. Credential collection stays in existing dedicated system flows.
4. [Microsoft Adaptive Cards universal actions](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/universal-action-model) describes action execution and refreshed card state after approval. Apply the lesson that an acted-on card must not remain apparently actionable. For Sevra, derive current control status from durable receipts while keeping the original result/effect evidence intact; do not silently rewrite historical numbers into current data.
5. [Apple buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) emphasizes meaningful labels, recognizable controls and limited prominent actions. [Apple text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields) covers persistent labels, logical keyboard traversal, contextual validation and locale-aware numeric presentation. Use system controls and one primary submit action, retaining exact Decimal/date semantics underneath. Newer platform styling is not a macOS 14 requirement.

## Alternatives and scope judgment

Recommended: a small host-owned conversation surface schema referencing existing visual and operation contracts. Questions and forms should work before general charts/diagrams. Business forms use their existing definitions; ad hoc clarifications use bounded typed fields. The first release does not need a universal remote UI standard, webview/HTML, arbitrary script callbacks, a new workflow engine, a full dashboard in every message, or a stored mini-app package for each question.

Useful inline content includes short choice questions, missing-input forms, exact change previews and receipts, small source-linked tables/charts, record picks and artifact previews. Large boards, detailed graphs, bulk editable tables and long forms should expand into a focused workspace while keeping the same conversation, draft and selection. All underlying operations remain available by text.

The unresolved implementation questions are measured row/focus performance, the minimal durable input handoff, and adapting existing field/editor dependencies without cycles. The owning plan makes these explicit gates. No usability outcome or local-model completion rate is established by this source review.
